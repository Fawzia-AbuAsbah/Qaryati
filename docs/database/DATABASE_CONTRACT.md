# Qaryati — Database Contract v1 (PROPOSED)

> **Status:** team review required before merge. Based on the Fall 2026 project brief and current Modular Monolith packaging. The specification does NOT prescribe exact tables; names and constraints below are proposed engineering decisions.

## 1. Conventions and principles

- PostgreSQL 17, schema `public`, UTF-8, Flyway-managed DDL. `spring.jpa.hibernate.ddl-auto=none`.
- Table/column names: lower `snake_case`; plural table names. Primary keys are `BIGINT GENERATED BY DEFAULT AS IDENTITY` except many-to-many join tables with composite PKs.
- Times are `TIMESTAMPTZ` in UTC at the application boundary; business reference years use `INTEGER`, exact dates use `DATE`.
- Personal credentials never in migrations or Git. `password_hash` contains secure adaptive hash only.
- Every village has one governorate; local authority is optional and must be in the same governorate. `archived_at` marks archived villages.
- Most master data relationships use `ON DELETE RESTRICT` to protect historical records. Join associations cascade only when their parent association is deleted.
- Provisional status vocabulary is `DRAFT / UNDER_REVIEW / VERIFIED / REJECTED` with `DISPUTED` on evidentiary records.
- Each population observation has a **mandatory** source and unique `(village, year, methodology, source)`; conflicting counts from different sources coexist.
- Sources for village, history, events, sites and heritage are represented with typed associative tables and enforceable foreign keys.
- Generic audit, verification and conflict targets are **polymorphic** `(entity_type,entity_id)` and therefore cannot be protected by a normal FK; application policy + integration tests must enforce references.
- Role authorization decisions and authorization-sensitive write rules remain application-level responsibilities.
- API search/sort/pagination, validation, audit interception, retries, throttling and Docker cannot be guaranteed by SQL alone.

- Composite PKs: user_roles(user_id,role_id), village_sources(village_id,source_id), history_sources(village_history_id,source_id), event_sources(event_id,source_id), heritage_site_sources(heritage_site_id,source_id), cultural_heritage_sources(cultural_heritage_id,source_id).
- Composite UQs: local_authorities(governorate_id,name_ar), local_authorities(id,governorate_id), villages(governorate_id,name_ar), village_names(village_id,name,language_code,name_type), population_records(village_id,reference_year,methodology,source_id), cultural_heritage(village_id,name,heritage_type), village_agriculture(village_id,product_id), economic_activities(village_id,name,activity_type), geocoding_cache(provider,query_hash).
- Additional FK: villages(local_authority_id,governorate_id) → local_authorities(id,governorate_id), default MATCH SIMPLE and ON DELETE NO ACTION. A null authority is allowed; an assigned authority must share the village's governorate. The separate authority FK uses RESTRICT.
- The five citation joins cascade when their domain parent is deleted and restrict source deletion. user_roles cascades on user deletion and restricts role deletion. Other single-column FKs use RESTRICT, including audit actor, reviewer, and conflict resolver.
- users.email has a unique expression index on lower(email); it is not a plain-column UQ.

## 5. Important constraints and business rules

1. Village names unique within governorate by Arabic canonical name; this is a **provisional** disambiguation policy and may need review for duplicated historical names.
2. Coordinates must be valid latitude/longitude and both present or both absent. No separate GIS/PostGIS requirement has been imposed.
3. Population is never stored as a single field in `villages`; values are historical, cited observations. No constraint forces one definitive population per year.
4. EXACT requires event_date and null year_from/year_to; YEAR requires only year_from; PERIOD requires both ordered years; UNKNOWN requires all date fields null. Year fields remain limited to 1–2200. Exact DATE values are not subject to that range in SQL; applying a uniform range or supporting BCE/uncertain centuries remains a team decision.
5. Verification decisions and conflicts remain traceable: keep `audit_logs` immutable via application permissions; no silent overwrite of competing cited observations.
6. Rows marked `VERIFIED` require authorization and review workflow enforcement in services; SQL status CHECK alone cannot guarantee review took place. See proposed source requirements below.
7. SQL does **not** automatically update `updated_at`; services/JPA auditing or trigger strategy must be agreed and tested.
8. FK-indexes are created for principal read paths. Search may require `pg_trgm` or full-text indexing after actual workload measurements.
9. Duplicated source links are protected by compound PK; the source itself is a reusable bibliographic record.
10. Relations between villages are directional; the reciprocal relationship is not inserted automatically.

### Actor retention and conflict resolution

Disable users with users.enabled=false instead of deleting them. Audit rows retain a nullable user FK with ON DELETE RESTRICT and a mandatory nonblank actor_label captured at write time. Human actions retain the authenticated user ID plus a durable snapshot label; system actions use a stable system label with no user ID. Do not reconstruct past labels from mutable display names. SQL guarantees a nonblank label and protects referenced users; services must authenticate actors, assign labels, redact secrets from snapshots, and enforce append-only access. The policy does not prohibit deleting an entirely unreferenced user at SQL level.

RESOLVED conflicts require resolved_by, resolved_at, and nonblank resolution_notes, with resolved_at >= created_at. OPEN and IN_REVIEW require all three resolution fields null. Reopening must preserve the previous resolution in audit history before clearing those fields. The resolver FK restricts deletion. Human-only resolution, no draft resolution notes, and reopening behavior are proposed policies requiring sign-off; SQL enforces row consistency but cannot enforce audit capture.

### Verification source requirements (proposed service policy; team approval required)

| Record being verified | Required evidence |
|---|---|
| population_records | Its mandatory source_id (already enforced for every status) |
| villages | At least one village_sources association |
| village_histories | At least one history_sources association |
| historical_events | At least one event_sources association |
| heritage_sites | At least one heritage_site_sources association |
| cultural_heritage | At least one cultural_heritage_sources association |

Draft historical/heritage records may have no citations. Owning services must check source links, authorization, and review outcome and record the verification decision plus status transition in one transaction. Citation removal from verified records must use the same per-target locking discipline as verification and either reject removal of the last source or explicitly return the record to review with an audit entry; the choice requires approval. A source link does not prove the source supports the claim: reviewers assess relevance. Ordinary FKs and status checks do not enforce minimum citation counts. Agriculture/community provenance remains deferred; the policy does not introduce tables.

### Cross-module API ownership and dependency direction (proposed)

Arrows below mean Java compile-time dependency on the provider's public API. Interfaces and DTOs belong to the provider; exact signatures and named-interface exposure remain to be implemented and approved.

| Consumer | Provider API and responsibility |
|---|---|
| Population, Heritage, Agriculture, Community | Village: village identity/availability lookup |
| Village | Integration: provider-neutral geocoding |
| Village, Population, Heritage, Agriculture, Community | Security: authenticated actor and authorization context |
| Village, Population, Heritage, Agriculture, Community, Security | Data Quality: source lookup, typed citation operations, audit append, review/conflict recording |

Data Quality owns sources, all five citation joins, audit_logs, verification_records, and data_conflicts. Domain owners retain their records and verification status; they coordinate transactions, validate target existence and eligibility, and call Data Quality with scalar target IDs and trusted actor snapshots. Data Quality validates source IDs and owns citation persistence, but never imports domain or Security entities/repositories or calls back into consumer services. Security can call Data Quality to audit security operations; Data Quality receives the actor from the caller rather than querying Security. Read FK IDs as scalars across boundaries instead of cross-module JPA entity associations. FK constraints remain the final integrity guard.

Data Quality and Integration may depend on Common technical utilities; Common has no business-module dependencies. Security depends only on Data Quality/Common for this flow. Village may depend on Integration, Security, and Data Quality; other domain modules may additionally depend on Village. No reverse dependency is allowed. Cross-domain verification endpoints must live in the owning domain module; a central Data Quality controller must not orchestrate callbacks into domain modules. Generic target validation occurs at the owning service boundary; audit DELETE targets may intentionally outlive deleted records. Composite-key association changes are audited against their owning scalar-ID record with the full pair included in the snapshot.

## 6. Known design decisions requiring team sign-off

| Decision | Proposed default | Alternatives / risk |
|---|---|
| Keys | BIGINT identity | UUID if offline/client-generated keys required |
| Cross-module FK | Real FK to `villages.id` and `sources.id` | Schema isolation would complicate integrity |
| Provenance | Typed joins + mandatory population source | Generic polymorphic links lose FK validation |
| Village delete | Archive (`archived_at`) and restrict physical delete | Cascade would destroy evidence |
| Location | Numeric WGS84 lat/lon | PostGIS optional for radius/adjacency queries |
| Historical dates | EXACT uses only event_date; year fields use 1–2200 | Decide uniform exact-date range and BCE/uncertain-date support |
| Security | users/roles join; future privilege policy in Java | Database permissions model optional |
| Event registry | Not included | Revisit if persistent Spring Modulith events adopted |
| Community agriculture sources | No direct source associations in v1 | Add typed citation joins if evidence requirements broaden |

Additional choices requiring team approval: durable human/system actor-label format and retention/privacy policy; disabling users and RESTRICT retention; human-only conflict resolution with nonblank notes and no draft resolution fields; reopening policy; verification citation minimums and last-citation removal behavior; the API dependency graph above; future runtime schema configuration below. The SQL corrections implement the documented proposed defaults for review, not final business-policy acceptance.

## 7. Flyway usage and team workflow

1. Review diagram and columns with all 4 module owners. Do not merge without approval.
2. Work on a feature branch, then PR into `main`. Place `V1__initial_schema.sql` under `src/main/resources/db/migration/`.
3. Test migrations on a brand-new disposable `qaryati_db`, run `./mvnw test`, run app, verify `flyway_schema_history` and `\dt`.
4. Never edit an already-merged/applied Flyway script. Subsequent changes get `V2__...sql`, `V3__...sql` etc.
5. Run another fresh database test plus upgrade test before each migration PR.
6. Do not commit local passwords, `.idea/workspace.xml`, build outputs, PostgreSQL data directories or production data exports.

### V1 application evidence and explicit schema

On 2026-10-16 the owner reported zero rows in local public.flyway_schema_history and confirmed V1 was never shared and nobody else ran it. Repository history alone cannot prove remote application status. That owner confirmation authorizes correcting this unapplied V1. An empty history table alone would not establish the absence of pre-existing objects; deployment must still confirm an empty target separately.

All domain CREATE TABLE, ALTER TABLE, REFERENCES, and index target tables in V1 explicitly use public. PostgreSQL's public schema must already exist and the migration role must have the required privileges. This fixes DDL placement without relying on search_path. Runtime configuration is unchanged in this pass. Before deployment, align Flyway metadata and ORM resolution explicitly with:

```properties
spring.flyway.default-schema=public
spring.flyway.schemas=public
spring.jpa.properties.hibernate.default_schema=public
```

These are recommended future settings, not settings already added to application.properties. V1 cannot configure where Flyway creates its own history table. Keep the agreed 27 domain tables plus Flyway metadata; do not add tables for these corrections.
