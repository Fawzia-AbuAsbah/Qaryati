# Historical Events Foundation

Implemented under `com.qaryati.heritage` on `Balsam/historical-events-foundation`.
V1 is authoritative; the database contract still marks several policies as proposed.
This foundation has no dependency on Population Records.

## Components

- `HistoricalEvent`: field-access JPA entity for `public.historical_events`, with exactly
  the V1 columns. Village is a scalar FK ID, with no import of Village internals.
  Identity is database generated. `created_at` is generated by PostgreSQL and read
  back by Hibernate; there is no `updated_at` field. No public setters expose IDs,
  timestamps, village reassignment, or verification transitions.
- `DatePrecision`: EXACT, YEAR, PERIOD, UNKNOWN.
- `VerificationStatus`: DRAFT, UNDER_REVIEW, VERIFIED, REJECTED, DISPUTED.
- Request and response records, a mapper, and Jakarta field and cross-field validation.
  Requests contain only editable content and village ID, with no server-managed fields.
  Titles and descriptions are required and nonblank; title maximum is 250 characters.
  Nonblank validation is an application rule; V1 itself enforces NOT NULL rather than nonblank.
- Domain creation always produces DRAFT. `reviseDraft` validates before modifying fields,
  preserves identity, village, creation timestamp and status, and rejects every non-DRAFT
  status. `requireDraftMutation` is also available as a local prerequisite for a future
  deletion flow. Neither method grants authorization. There is no deletion service.
- Internal Spring Data repository with village-scoped single-record lookup and pagination.
  `findVillagePage(villageId, page, size)` uses fixed ascending unique ID ordering.
  This is deterministic for a stable dataset; it does not promise snapshot consistency
  across concurrent transactions. Repository methods are not visibility-filtered APIs.

## Date rules

| Precision | eventDate | yearFrom | yearTo |
|---|---|---|---|
| EXACT | required | null | null |
| YEAR | null | required | null |
| PERIOD | null | required | required, at least yearFrom |
| UNKNOWN | null | null | null |

Both year fields, when present, must be within 1–2200. Equal period endpoints are valid.
No exact-date year range, future-date restriction, or event-date chronology rule is added.
The same combinations are checked on DTOs, entities, domain mutations, and in V1 SQL.

## Tests and safety

Run database-free tests explicitly, from PowerShell with Java 21 and Maven available:

```powershell
.\mvnw.cmd '-Dtest=com.qaryati.heritage.HistoricalEventTest,com.qaryati.heritage.HistoricalEventDatabaseGuardTest' test
```

The unit tests cover all 32 precision/field-presence combinations on DTOs, entities
and domain construction; year boundaries and ordering; required fields; title limits;
mapper fields; server-managed field preservation; and draft mutation restrictions.
Guard unit tests reject unsafe configuration without opening database connections.

Do not run the integration class or an unrestricted Maven test command until the dedicated
test database has been independently verified. Do not use `qaryati_db` or a shared database.
The existing `test` profile uses `localhost:5432/qaryati_test_db`, user `postgres`, and
`DB_PASSWORD`. Obtain the password through your normal local secret mechanism; never
put credentials in tracked files or command output.

First independently verify the connection and identity in PowerShell:

```powershell
# Requires psql on PATH and DB_PASSWORD already set securely in this session.
$env:PGPASSWORD = $env:DB_PASSWORD
try {
    psql -X -h localhost -p 5432 -U postgres -d qaryati_test_db -v ON_ERROR_STOP=1 `
        -c 'SELECT current_database(), current_user, version();'
    if ($LASTEXITCODE -ne 0) { throw 'Database verification failed' }
} finally {
    Remove-Item Env:PGPASSWORD -ErrorAction SilentlyContinue
}
```

Confirm the result is PostgreSQL, database `qaryati_test_db`, user `postgres`, and confirm
operationally that this database is dedicated to tests. A matching name alone does not
prove a database contains no valuable data. Only after that verification, run:

```powershell
.\mvnw.cmd '-Dtest=com.qaryati.heritage.HistoricalEventRepositoryIntegrationTest' `
    '-Dspring.profiles.active=test' '-Dqaryati.heritage-tests.database-verified=true' test
```

The initializer requires the test profile, explicit verification flag, exact dedicated
JDBC URL, and rejects alternate connection URLs. Before Spring context refresh or Flyway,
it opens a JDBC connection and checks the live product, database and user identity.
The test configuration supplies the same fixed DataSource and locks Flyway credentials
to the verified connection. Flyway clean stays disabled, Hibernate only validates, and
JPA schema generation is disabled. There is no H2 fallback or automatic database creation.
Flyway may initialize the dedicated database; that migration is outside test rollback.
Each test uses isolated generated fixtures and transaction rollback, without cleanup SQL.
Identity sequences can advance even after rollback. Constraint tests use direct SQL to
bypass Jakarta validation and assert PostgreSQL SQLSTATEs, with no SQL after an error.

Integration coverage includes all date combinations, ranges, status vocabulary,
required columns, title length, V1 defaults, persistence for every precision and status,
draft updates, village lookup isolation, deterministic pagination, foreign key integrity
and restricted parent deletion. Village/governorate SQL is test-fixture setup only;
production code does not access another module's tables or Java internals.

### Foundation verification in the implementation environment

58 database-free test invocations passed, with zero failures, errors or skips.
All test sources, including the integration class, compiled. The 59 PostgreSQL
integration invocations were not executed: `DB_PASSWORD` was unavailable and the
dedicated database identity could not be independently verified. These are unexecuted
tests, rather than tests reported as skipped by JUnit. The supplied wrapper failed
to start in this environment, so the cached Maven 3.9.11 executable was used offline
with an explicit local repository path. The available runtime was JDK 22; compilation
targeted Java 21 (`release 21`). Running on an actual JDK 21 remains a local verification step.

## Limitations and required contracts

No controller, application service, production write operation, restricted read endpoint,
status transition workflow, or source association operation is activated. Internal JPA
repository access must not be mistaken for a safe application API. Domain guards cannot
protect direct SQL, bulk updates or repository deletion; future services must enforce them.

Provider-owned public interfaces and policies must be agreed before activation:

1. Security: trusted actor identity, role/action authorization, village scope, visibility
   for draft/review/rejected/disputed records, and consistent forbidden/not-found behavior.
2. Village: identity and availability lookup, archive rules, and transaction/concurrency
   semantics for eligibility checks. An FK alone does not establish availability.
3. Data Quality: source existence and eligibility, typed `event_sources` operations,
   transactional audit append with actor snapshots and before/after data, review/conflict
   recording, and entity target naming. Heritage must not import provider internals.
4. Verification: approved status transitions, reviewer authorization, citation requirements
   (the contract proposes at least one event source for verification), source removal,
   disputed/rejected record handling, and locking coordination with citation changes.
5. Mutation and read policies: approve endpoint contracts, draft deletion and citation/audit
   retention, pagination limits, concurrency control, and visibility-filtered repository queries.
   V1 supplies no optimistic version column; do not assume lost updates are prevented.

After these agreements, add transactional services, authorization and audit integration,
visibility filtering, then controllers and full integration/security/concurrency tests.
No permissive authorization fallback, fake provider implementation, or no-op audit is included.
